# 容器运行时与 Kubernetes 集群安装

> **核心理解**：Kubernetes 不直接创建容器。kubelet 通过 CRI 调用容器运行时，容器运行时再通过底层 Linux 和 CNI 创建 Pod 的运行环境。

## §0 心智模型：从 kubelet 到容器

```text
kubectl
  ↓ HTTPS
kube-apiserver
  ↓ PodSpec
kubelet
  ↓ CRI gRPC
containerd
  ├── containerd-shim
  ├── runc
  ├── 镜像存储
  ├── Snapshotter
  └── CNI 调用
        ↓
    Pod Sandbox
        ↓
      容器
```

三个接口的职责：

| 接口 | 参与者 | 解决的问题 |
|---|---|---|
| CRI | kubelet ↔ containerd | 管理 Pod Sandbox、容器和镜像 |
| CNI | kubelet/运行时 ↔ 网络插件 | 给 Pod 配置网络和 IP |
| CSI | kubelet ↔ 存储插件 | 挂载、卸载和供应存储 |

> **关键边界**：containerd 负责运行容器；CNI 负责网络；CSI 负责存储；kubelet 负责让节点上的 Pod 达到 API 中声明的状态。

## §1 Containerd 架构

### 1.1 Containerd 为什么存在

Docker Engine 是面向开发者的完整产品，Containerd 更接近容器运行时核心。Kubernetes 通过 CRI 使用 Containerd，不需要依赖 Docker CLI 或 Docker Engine。

### 1.2 分层结构

```text
客户端层：ctr / nerdctl / crictl / kubelet
        ↓
服务层：containerd daemon
        ↓
插件层：镜像、元数据、Runtime、Snapshotter、CNI
        ↓
底层：runc、Linux namespace、cgroup、overlayfs、网络设备
```

### 1.3 Namespace

Containerd 的 namespace 用于隔离资源视图。Kubernetes 的容器通常位于 `k8s.io` namespace 中：

```bash
ctr namespaces list
ctr -n k8s.io containers list
nerdctl --namespace k8s.io ps
```

如果不指定 `-n k8s.io`，可能会误以为 Kubernetes 没有容器或镜像。

### 1.4 版本和配置意识

课堂资料中出现的 Containerd 版本、镜像加速目录和 sandbox 镜像路径可能随版本变化。实际操作时先检查：

```bash
containerd --version
containerd config dump
systemctl status containerd
```

不要直接把旧版本的配置文件覆盖到新版本；先生成当前版本的默认配置，再修改必要字段。

## §2 ctr、nerdctl 与 crictl

### 2.1 `ctr`

`ctr` 是 Containerd 的底层调试客户端，功能直接、参数偏底层：

```bash
ctr version
ctr namespaces list
ctr -n k8s.io images list
ctr -n k8s.io containers list
ctr -n k8s.io tasks list
ctr -n k8s.io images pull docker.io/library/nginx:latest
```

特点：

- 面向 Containerd 原生 API
- 参数不追求 Docker 兼容
- 适合检查 namespace、镜像、container、task
- 某些镜像仓库需要指定 hosts 目录

### 2.2 `nerdctl`

`nerdctl` 提供接近 Docker 的用户体验，但底层直接连接 Containerd：

```bash
nerdctl --namespace k8s.io images
nerdctl --namespace k8s.io ps -a
nerdctl --namespace k8s.io run -d --name web -p 8080:80 nginx
nerdctl --namespace k8s.io exec -it web sh
nerdctl --namespace k8s.io logs web
nerdctl --namespace k8s.io inspect web
nerdctl --namespace k8s.io network ls
nerdctl --namespace k8s.io volume ls
```

课堂环境还涉及：

- `run`
- `rm`
- `prune`
- `rename`
- `stop` / `start` / `restart`
- `pause` / `unpause`
- `kill`
- `exec`
- `cp`
- `inspect`
- `logs`
- `port`
- `commit`
- `save` / `load`
- `tag` / `push`

### 2.3 `crictl`

`crictl` 是 Kubernetes CRI 的调试工具，观察对象更接近 kubelet：

```bash
crictl version
crictl info
crictl pods
crictl ps
crictl ps -a
crictl images
crictl inspect <container-id>
crictl inspectp <pod-id>
crictl logs <container-id>
crictl exec -it <container-id> sh
```

配置文件通常位于 `/etc/crictl.yaml`，重点是 runtime endpoint：

```yaml
runtime-endpoint: unix:///run/containerd/containerd.sock
image-endpoint: unix:///run/containerd/containerd.sock
timeout: 10
 debug: false
```

> 注意：上面的 `debug` 前有一个空格只是排版示意，实际 YAML 必须正确缩进。

### 2.4 工具选择

| 现象 | 优先工具 |
|---|---|
| Kubernetes 看不到 Pod | `kubectl` |
| kubelet 需要确认 CRI 状态 | `crictl` |
| 需要看 Containerd 原生对象 | `ctr` |
| 需要用 Docker 风格操作容器 | `nerdctl` |
| 需要看服务状态 | `systemctl`、`journalctl` |

## §3 Kubernetes 节点的 Linux 前置条件

### 3.1 关闭或正确处理 Swap

Kubernetes 节点通常要求关闭 swap，避免 kubelet 的资源管理和调度判断失真：

```bash
swapoff -a
sed -i.bak '/\sswap\s/d' /etc/fstab
free -h
```

### 3.2 加载内核模块

课堂实验使用：

```bash
modprobe overlay
modprobe br_netfilter
modprobe ip_vs
modprobe ip_vs_rr
modprobe ip_vs_wrr
modprobe ip_vs_sh
modprobe nf_conntrack
```

持久化：

```bash
cat >/etc/modules-load.d/k8s.conf <<'EOF'
overlay
br_netfilter
ip_vs
ip_vs_rr
ip_vs_wrr
ip_vs_sh
nf_conntrack
EOF
```

### 3.3 sysctl 参数

```bash
cat >/etc/sysctl.d/99-kubernetes.conf <<'EOF'
net.bridge.bridge-nf-call-iptables = 1
net.bridge.bridge-nf-call-ip6tables = 1
net.ipv4.ip_forward = 1
vm.swappiness = 0
EOF
sysctl --system
```

含义：

- `bridge-nf-call-iptables`：让桥接流量进入 iptables 处理路径
- `ip_forward`：允许节点转发 IPv4 数据包
- `vm.swappiness=0`：减少 swap 对容器资源管理的干扰

验证：

```bash
lsmod | egrep 'overlay|br_netfilter|ip_vs'
sysctl net.ipv4.ip_forward
sysctl net.bridge.bridge-nf-call-iptables
```

### 3.4 主机名、解析和时间

集群节点必须能够稳定解析彼此的主机名，且时间同步：

```bash
hostnamectl set-hostname master
getent hosts worker1
getent hosts worker2
timedatectl
systemctl status chrony
```

## §4 Containerd 为 Kubernetes 做的配置

### 4.1 SystemdCgroup

现代 Kubernetes + Containerd 通常需要统一使用 systemd cgroup 驱动。不同 Containerd 版本配置路径不同，先检查配置结构：

```bash
containerd config default > /etc/containerd/config.toml
grep -n 'SystemdCgroup' /etc/containerd/config.toml
```

常见配置思想：

```toml
[plugins."io.containerd.grpc.v1.cri".containerd.runtimes.runc.options]
  SystemdCgroup = true
```

修改后：

```bash
systemctl restart containerd
systemctl is-active containerd
```

### 4.2 Sandbox 镜像

Pod Sandbox 通常使用 pause 镜像。实际镜像名称应与 Kubernetes 版本和镜像仓库策略一致：

```bash
crictl info | grep -i sandbox -C 2
```

### 4.3 镜像加速

镜像加速配置属于环境相关内容，不要把某个临时镜像站地址当成永久标准。建议：

1. 先选择可靠的内部或云厂商镜像仓库
2. 为 `docker.io` 和 `registry.k8s.io` 分别配置
3. 使用 `ctr`、`nerdctl`、`crictl` 分别验证
4. 记录当前配置和回滚方法

### 4.4 配置检查

```bash
systemctl status containerd
journalctl -u containerd -b --no-pager
crictl info
crictl images
```

## §5 kubeadm 集群安装流程

### 5.1 安装方式

| 方式 | 用途 |
|---|---|
| kubeadm | 学习和搭建接近真实的集群 |
| kind / minikube | 快速本地开发和 API 实验 |
| 二进制安装 | 理解组件细节，不适合初始学习 |
| 托管 Kubernetes | 学习云上生产能力 |

本课堂主线是 kubeadm。

### 5.2 节点规划

```text
master30：控制平面
worker31：工作节点
worker32：工作节点
client：kubectl 客户端（可选）
```

16GB 主机不必长期同时启动全部节点；按实验需要启停。

### 5.3 典型安装顺序

```text
所有节点：
  Ubuntu 初始化
  主机名和解析
  SSH
  时间同步
  关闭 swap
  内核模块和 sysctl
  Containerd
  kubelet / kubeadm / kubectl

控制平面：
  kubeadm init
  配置 kubeconfig
  部署 CNI

Worker：
  kubeadm join

最后：
  kubectl get nodes
  kubectl get pods -A
```

### 5.4 初始化时需要明确的参数

- Kubernetes 版本
- Pod CIDR
- Service CIDR
- API Server 地址
- CNI 要求的 Pod 网络范围
- Containerd socket
- kubelet cgroup 驱动

Pod CIDR 必须和 CNI 配置匹配，否则节点可能长期 `NotReady` 或 Pod 网络异常。

### 5.5 初始化和 kubeconfig

```bash
kubeadm init \
  --apiserver-advertise-address=<control-plane-ip> \
  --pod-network-cidr=<pod-cidr> \
  --cri-socket=unix:///run/containerd/containerd.sock
```

普通用户使用 kubectl 前需要配置：

```bash
mkdir -p "$HOME/.kube"
cp -i /etc/kubernetes/admin.conf "$HOME/.kube/config"
chown "$(id -u):$(id -g)" "$HOME/.kube/config"
```

`admin.conf` 具有高权限，不应随意复制到不可信机器。

### 5.6 节点加入

控制平面初始化成功后生成 join 命令：

```bash
kubeadm token create --print-join-command
```

Worker 执行类似：

```bash
kubeadm join <api-server>:6443 \
  --token <token> \
  --discovery-token-ca-cert-hash sha256:<hash> \
  --cri-socket=unix:///run/containerd/containerd.sock
```

### 5.7 重置集群

实验重做前可以使用：

```bash
kubeadm reset -f
rm -rf "$HOME/.kube"
```

重置不会自动清理所有 CNI、iptables、IPVS、挂载点和旧数据；重建前要按实际情况清理。

## §6 Calico 网络与节点加入

安装 CNI 前，节点可能显示：

```text
NotReady
```

常见原因是网络插件尚未部署。部署后检查：

```bash
kubectl get pods -n kube-system
kubectl get nodes -o wide
kubectl get events -A --sort-by=.lastTimestamp
```

Calico 配置中最关键的是 Pod 网络范围匹配。检查：

```bash
kubectl cluster-info dump | grep -m1 cluster-cidr
kubectl get ippools.crd.projectcalico.org -o yaml
```

如果修改 Calico YAML，重点确认：

- Pod CIDR
- 镜像版本
- RBAC
- 节点 IP 自动发现方式
- BGP 或 VXLAN 模式
- 宿主机内核和防火墙

> 课堂资料以 Calico 为例。实际生产还需要理解 Cilium、Flannel 等插件的取舍，不要把“能安装 Calico”当成已经理解 CNI。

## §8 常见故障

| 现象 | 优先排查 |
|---|---|
| `kubeadm init` preflight 失败 | swap、端口、内核模块、Containerd、主机名 |
| Node 一直 NotReady | kubelet、CNI、Pod CIDR、Containerd、证书 |
| Pod 一直 ContainerCreating | 镜像、CNI、Volume、Sandbox |
| `crictl` 无法连接 | runtime endpoint、Containerd socket |
| kubectl 连接拒绝 | kubeconfig、API Server、6443 端口 |
| 节点能加入但网络不通 | CNI Pod、路由、iptables、内核参数 |
| 镜像拉取失败 | 仓库地址、DNS、证书、镜像加速 |
| kubelet 启动失败 | cgroup、swap、配置文件、端口、证书 |

标准排查：

```bash
systemctl status kubelet containerd
journalctl -u kubelet -b --no-pager
journalctl -u containerd -b --no-pager
crictl info
kubectl get pods -A -o wide
kubectl get events -A --sort-by=.lastTimestamp
```

## §10 易错点

1. `ctr`、`nerdctl`、`crictl` 不是同一个层次的工具。
2. 不指定 Containerd namespace，可能看不到 Kubernetes 的镜像和容器。
3. kubelet 通过 CRI 使用运行时，不要求安装 Docker Engine。
4. CNI 不等于 kube-proxy。
5. Pod CIDR 和 CNI 的网络范围必须匹配。
6. 关闭 swap 后还要检查 `/etc/fstab`，否则重启可能重新启用。
7. `SystemdCgroup` 要和 kubelet 的 cgroup 驱动一致。
8. `admin.conf` 是高权限凭据。
9. `kubeadm reset` 不等于完整清理所有网络规则和挂载。
10. 旧课堂命令中的版本号和镜像站地址不能直接照搬到新版本。

## §11 面试追问

### Q1：Kubernetes 为什么不直接调用 runc？

因为 kubelet 需要统一的容器运行时接口。CRI 把 kubelet 与具体运行时解耦，Containerd 再负责调用 runc 或其他底层 runtime。

### Q2：Containerd、CRI 和 CNI 的关系？

Containerd 是运行时，CRI 是 kubelet 调用运行时的接口，CNI 是为 Pod 配置网络的插件接口。三者不是同一种东西。

### Q3：为什么安装 CNI 后 Node 才变成 Ready？

kubelet 不只检查自身进程，还需要节点具备可用的 Pod 网络条件。网络插件负责创建和配置 Pod 网络。

### Q4：`crictl` 和 `kubectl` 的区别？

kubectl 通过 API Server 观察集群对象；crictl 直接通过 CRI 观察节点上的 Pod Sandbox、容器和镜像。
