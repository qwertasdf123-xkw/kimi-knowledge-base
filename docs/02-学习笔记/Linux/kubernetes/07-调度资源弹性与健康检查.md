# Kubernetes 调度、资源弹性与健康检查

> **核心理解**：资源管理控制 Pod 能否被调度和是否能稳定运行；探针控制 Pod 是否能进入 Service 流量路径或是否需要重启。

## §0 资源管理总览

```text
节点容量
  ↓
Pod Request 资源
  ↓
Scheduler 调度
  ↓
kubelet 通过 cgroup 限制
  ↓
Container Runtime 实际占用
  ↓
Metrics Server 收集指标
  ↓
HPA 调节副本
```

四个层级的限制和观察：

| 层级 | 作用 |
|---|---|
| Request | 调度和决策依据 |
| Limit | 容器内资源上限 |
| QoS | 节点资源紧张时的驱逐顺序 |
| Metrics | 实时观察和 HPA 输入 |

---

## §1 Metrics Server

### 1.1 作用

Metrics Server 从 Kubelet 收集 node 和 pod 的资源指标，并通过 Metrics API 暴露：

- `kubectl top node`
- `kubectl top pod`
- HPA
- VPA

Metrics Server 不是监控系统，不能替代 Prometheus 等长期方案。

### 1.2 部署

```bash
kubectl apply -f components.yaml
kubectl get pods -n kube-system | grep metrics
kubectl top node
kubectl top pod -A
```

常见调整：

```bash
sed -i '/metric-resolution/a\        - --kubelet-insecure-tls' components.yaml
```

证书严格化的生产集群需要根据 CA 重新签发并配置 `--kubelet-certificate-authority` 等参数。

### 1.3 故障现象

```text
error: Metrics API not available
```

常见原因：

- metrics-server Pod 异常
- kubelet 无法响应 API
- 证书不匹配
- API Server aggregator 配置异常

## §2 kubectl top 与指标使用

```bash
kubectl top node
kubectl top node --sort-by=memory
kubectl top pod -A
kubectl top pod -n dev --containers
```

kubectl top 不是监控体系，只是快速观察：

- 调度热点
- 资源热点
- HPA 误配置
- 节点压力大但 Pod 少的异常

## §3 Request 与 Limits

```yaml
resources:
  requests:
    cpu: 100m
    memory: 128Mi
  limits:
    cpu: 500m
    memory: 256Mi
```

| 字段                | 含义                  |
| ----------------- | ------------------- |
| `requests.cpu`    | 调度时为 Pod 预留的 CPU 份额 |
| `requests.memory` | 调度时为 Pod 预留的内存      |
| `limits.cpu`      | 容器 CPU 上限，可以被节流     |
| `limits.memory`   | 容器内存上限，超出后 OOMKill  |

常见陷阱：

- requests 过大 → Pod Pending
- limits 过大 → 节点压力
- limits 过小 → 应用被 OOMKill

CPU 是可压缩资源，超额会被节流；内存是不可压缩资源，超额会被杀。

---

## §4 QoS Class

QoS 不是用户配置，而是根据 requests 和 limits 自动计算：

| QoS        | 条件                             | 节点资源紧张时 |
| ---------- | ------------------------------ | ------- |
| Guaranteed | 每个容器 limits 和 requests 都被设置且相等 | 最后被驱逐   |
| Burstable  | 部分设置 requests 或 limits         | 次之驱逐    |
| BestEffort | 都没有设置                          | 最先驱逐    |

QoS 影响：

- Pod 调度到节点的方式
- 节点资源紧张时的驱逐顺序
- OOM 时 Pod 被杀死的优先级

生产建议：

- 关键应用尽量保证 QoS 为 Guaranteed 或 Burstable
- 临时任务可以使用 BestEffort，但要意识到驱逐顺序

## §5 ResourceQuota

ResourceQuota 在 Namespace 上限流对象数量和资源总和：

```yaml
apiVersion: v1
kind: ResourceQuota
metadata:
  name: dev-quota
  namespace: dev
spec:
  hard:
    pods: 20
    requests.cpu: "4"
    requests.memory: 8Gi
    limits.cpu: "8"
    limits.memory: 16Gi
    persistentvolumeclaims: 10
    services: 20
    secrets: 30
    configmaps: 30
```

验证：

```bash
kubectl get resourcequota -n dev
kubectl describe resourcequota dev-quota -n dev
```

如果应用创建失败并出现 `exceeded quota`，需调整配额或优化资源使用。

## §6 LimitRange

LimitRange 在 Namespace 内部对 Pod、容器、PersistentVolumeClaim 等设置默认和约束：

```yaml
apiVersion: v1
kind: LimitRange
metadata:
  name: dev-limits
  namespace: dev
spec:
  limits:
    - type: Container
      default:
        cpu: 500m
        memory: 512Mi
      defaultRequest:
        cpu: 200m
        memory: 256Mi
      min:
        cpu: 100m
        memory: 128Mi
      max:
        cpu: "1"
        memory: 1Gi
```

行为：

- 没设置资源时：自动填入 `default` 和 `defaultRequest`
- 超过 `max` 时：创建失败
- 低于 `min` 时：创建失败

## §7 HPA

### 7.1 作用

HPA 根据指标调整 Deployment、ReplicaSet、StatefulSet 的副本数。常用指标：

- CPU
- Memory
- 自定义指标
- 外部指标

### 7.2 CPU 伸缩

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: web-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: web
  minReplicas: 2
  maxReplicas: 10
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 60
```

### 7.3 Memory 伸缩

```yaml
metrics:
  - type: Resource
    resource:
      name: memory
      target:
        type: AverageValue
        averageValue: 500Mi
```

### 7.4 伸缩窗口

```yaml
behavior:
  scaleUp:
    stabilizationWindowSeconds: 30
  scaleDown:
    stabilizationWindowSeconds: 300
```

控制连续高负载或连续低负载的判断时间，避免抖动。

### 7.5 制造压力验证

课堂常用工具：

```bash
ab -n 300000 -c 100 http://web/
hey -n 100000 -c 50 http://web/
```

```bash
# 内存压力
stress-ng --vm 2 --vm-bytes 800M --timeout 600
```

观察：

```bash
kubectl get hpa
kubectl top pod -l app=web
kubectl get pod -l app=web
```

### 7.6 HPA 不工作常见原因

- metrics-server 未运行
- Pod 没有 resources 设置
- 指标类型错误
- targetRef 错误
- HPA 与 VPA 重复
- 节点资源被其他负载占满

---

## §8 VPA 概念

VPA（Vertical Pod Autoscaler）自动调整容器 requests 和 limits：

- Recommender：根据历史数据建议值
- Updater：调整运行中 Pod 的资源
- Admission Controller：在 Pod 创建时修正

课堂资料中 VPA 作为概念理解，实际使用注意事项：

- VPA 和 HPA 不建议同时使用同一指标
- VPA 会重启 Pod
- VPA 不直接适用于有状态稳定运行时长要求的应用

## §9 健康检查三类探针

### 9.1 Startup Probe

```yaml
startupProbe:
  httpGet:
    path: /startup
    port: 8080
  failureThreshold: 30
  periodSeconds: 5
```

- 启动阶段判断应用是否完成启动
- 启动成功后其他探针才生效
- 适合慢启动、依赖外部服务启动的应用

### 9.2 Readiness Probe

```yaml
readinessProbe:
  httpGet:
    path: /healthz
    port: 8080
  initialDelaySeconds: 5
  periodSeconds: 10
  timeoutSeconds: 2
  successThreshold: 1
  failureThreshold: 3
```

- 失败 → Pod Ready=false
- Pod 从 Service Endpoint 移除
- 流量不再直接转发到该 Pod
- 不会导致重启

### 9.3 Liveness Probe

```yaml
livenessProbe:
  httpGet:
    path: /healthz
    port: 8080
  periodSeconds: 10
  failureThreshold: 3
```

- 失败 → kubelet 重启容器
- 适合检测死锁、卡住进程

### 9.4 行为对比

| 探针 | 失败行为 | 典型用途 |
|---|---|---|
| Startup | 启动期间不通过则继续检测 | 慢启动 |
| Readiness | 流量脱离 | 临时不可用、依赖外部服务 |
| Liveness | 容器重启 | 死锁、卡死、内存泄漏 |

---

## §10 探针的字段含义

| 字段 | 含义 |
|---|---|
| `initialDelaySeconds` | 容器启动后到开始探测的延迟 |
| `periodSeconds` | 探测周期 |
| `timeoutSeconds` | 探测超时时间 |
| `successThreshold` | 连续成功次数（liveness 必须为 1） |
| `failureThreshold` | 连续失败次数 |

Exec 探针：

```yaml
livenessProbe:
  exec:
    command:
      - sh
      - -c
      - test -f /tmp/healthy
```

TCP 探针：

```yaml
readinessProbe:
  tcpSocket:
    port: 8080
```

HTTP 探针：

```yaml
readinessProbe:
  httpGet:
    path: /healthz
    port: 8080
```

注意：HTTP 探针的状态码在 200–399 视为成功。

## §11 探针在 Scale Up 与滚动更新中的作用

### 11.1 Scale Up

```text
HPA 决策扩缩容
  ↓
Deployment 创建新 Pod
  ↓
Pod Running
  ↓
Readiness 通过
  ↓
加入 Service 后端
```

如果 Readiness 没通过：

- HPA 看似扩容成功
- 实际可用副本没增加
- 流量高峰可能过载其他 Pod

### 11.2 滚动更新

```text
Deployment 创建新 ReplicaSet
  ↓
新 Pod 启动
  ↓
旧 Pod 仍然提供服务
  ↓
新 Pod Readiness 通过
  ↓
旧 Pod 缩容
```

没有 Readiness 探针时，旧 Pod 可能被过早终止，导致服务中断。

## §12 资源与探针的关系

资源是“能否被调度”，探针是“能否被流量访问”。两者经常被混在一起讨论。

实践建议：

- 关键应用设置 requests
- 关键应用设置 limits，但避免限制过小导致 OOMKill
- 关键应用设置 Readiness 和 Liveness
- 慢启动应用设置 Startup Probe，而不是把 `initialDelaySeconds` 设得过大
- HPA 指标所依赖的字段必须设置 requests
- 不要把 Readiness 路径当成业务可用性深度检测

---

## §13 易错点

1. requests 影响调度，limits 影响运行时。
2. CPU 超额被节流，内存超额被杀。
3. QoS 是按字段计算，不是用户配置。
4. HPA 需要 metrics-server 正常工作。
5. HPA 依赖的指标字段必须设置 requests。
6. VPA 和 HPA 不应同时使用 CPU/Memory 同一指标。
7. Liveness 失败会重启容器，不要在探针中模拟业务接口。
8. Readiness 失败不会重启容器，但会把 Pod 从流量中拿掉。
9. Startup Probe 通过后其他探针才生效。
10. Probe 失败可能造成滚动更新或扩容“看起来成功但实际不可用”。
11. Node NotReady 后，Pod 状态会先变 Unknown，再被控制器重新调度。
12. ResourceQuota 限制的是 Namespace 总量，不是单 Pod。

## §14 面试追问

### Q1：HPA 的工作原理？

HPA Controller 定期从 Metrics API 或自定义指标读取目标对象指标，根据当前副本数和指标对比计算期望副本数，并在 ReplicaSet/Deployment 中更新 replicas。

### Q2：为什么 HPA 不工作？

可能因为 metrics-server 异常、Pod 没有 requests、指标类型不匹配、targetRef 错误、被其他控制面占满资源或权限不足。

### Q3：QoS 怎么算？

根据 requests 和 limits 设置自动计算：Guaranteed 需要每个容器的 limits 和 requests 都设置且相等；Burstable 部分设置；BestEffort 都不设置。

### Q4：三种探针区别？

Startup 在启动期判断应用是否就绪；Readiness 判断是否接收流量，失败后从 Service 移除；Liveness 判断是否需要重启容器。
