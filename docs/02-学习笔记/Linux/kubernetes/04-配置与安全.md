# Kubernetes 配置与安全

> **核心理解**：应用配置解决“程序启动时需要什么”；认证回答“你是谁”；授权回答“你能做什么”；准入控制决定“请求是否允许进入系统”。

## §0 配置与安全总览

### 应用配置链

```text
ConfigMap / Secret
        ↓
环境变量或 Volume
        ↓
Pod 容器进程
```

### API 访问控制链

```text
客户端请求
  ↓ TLS / Transport Security
Authentication：你是谁？
  ↓
Authorization：你能做什么？
  ↓
Admission：这个请求是否符合策略？
  ↓
对象校验和持久化
```

### 两类身份

| 身份 | 典型使用者 |
|---|---|
| 普通 User | 人、外部客户端、证书用户 |
| ServiceAccount | Pod 内应用、控制器、自动化程序 |

## §1 ConfigMap

### 1.1 作用

ConfigMap 保存不敏感配置，例如：

- 环境名称
- 端口
- 配置文件
- 功能开关
- Nginx 页面内容

不要把密码、私钥等敏感信息放进 ConfigMap。

### 1.2 创建

```bash
kubectl create configmap app-config \
  --from-literal=APP_ENV=dev \
  --from-literal=APP_PORT=8080

kubectl create configmap nginx-config \
  --from-file=nginx.conf

kubectl get configmap app-config -o yaml
```

### 1.3 环境变量引用

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: config-env
spec:
  containers:
    - name: app
      image: busybox:1.36
      command: ["sh", "-c", "env; sleep 3600"]
      env:
        - name: APP_ENV
          valueFrom:
            configMapKeyRef:
              name: app-config
              key: APP_ENV
```

也可以批量引用：

```yaml
envFrom:
  - configMapRef:
      name: app-config
```

### 1.4 Volume 挂载

```yaml
volumes:
  - name: config
    configMap:
      name: nginx-config
containers:
  - name: nginx
    image: nginx:1.27
    volumeMounts:
      - name: config
        mountPath: /etc/nginx/conf.d
```

### 1.5 更新行为

- 通过环境变量注入的 ConfigMap 通常不会自动更新进程环境
- 通过 Volume 挂载的内容可能最终更新，但应用是否重新读取由应用决定
- 修改 ConfigMap 后需要验证应用是否感知
- 生产环境常通过 checksum Annotation 触发 Deployment 滚动更新

```bash
kubectl get configmap app-config -o yaml
kubectl describe pod <pod>
kubectl exec <pod> -- printenv
```

## §2 Secret

### 2.1 作用

Secret 用于保存：

- 密码
- Token
- TLS 证书
- 私钥
- 镜像仓库认证信息

Secret 中常见的 `data` 是 Base64 编码，不等于加密：

```bash
echo -n 'password' | base64
echo 'cGFzc3dvcmQ=' | base64 -d
```

因此还需要：

- 限制 RBAC 读取权限
- 保护 etcd
- 使用静态加密或外部密钥管理
- 不把 Secret 提交到 Git
- 不在日志中打印 Secret

### 2.2 创建

```bash
kubectl create secret generic db-secret \
  --from-literal=username=app \
  --from-literal=password='change-me'

kubectl get secret db-secret
kubectl get secret db-secret -o yaml
```

### 2.3 环境变量

```yaml
env:
  - name: DB_USER
    valueFrom:
      secretKeyRef:
        name: db-secret
        key: username
  - name: DB_PASSWORD
    valueFrom:
      secretKeyRef:
        name: db-secret
        key: password
```

### 2.4 Volume

```yaml
volumes:
  - name: tls
    secret:
      secretName: app-tls
containers:
  - name: app
    image: nginx:1.27
    volumeMounts:
      - name: tls
        mountPath: /etc/tls
        readOnly: true
```

### 2.5 Secret 类型

| 类型 | 用途 |
|---|---|
| `Opaque` | 通用键值 |
| `kubernetes.io/tls` | TLS 证书和私钥 |
| `kubernetes.io/dockerconfigjson` | 镜像仓库认证 |
| `kubernetes.io/basic-auth` | 基础认证信息 |
| `service-account-token` | 老式 ServiceAccount Token，需谨慎使用 |

## §3 Kubernetes API 访问控制链路

每个 API 请求通常经历：

```text
1. 传输安全：TLS
2. 认证：确认身份
3. 授权：判断权限
4. 准入控制：修改或拒绝对象
5. 对象校验
6. 持久化到 etcd
```

### 3.1 认证失败

典型现象：

```text
Unauthorized
You must be logged in to the server
x509: certificate signed by unknown authority
```

### 3.2 授权失败

典型现象：

```text
Error from server (Forbidden)
```

### 3.3 Admission 失败

典型现象：

- 资源违反策略
- Namespace 不允许创建某类对象
- Pod 安全策略拒绝
- Webhook 超时或拒绝

### 3.4 审计

Audit 用于记录 API 请求的身份、资源、动作和结果。生产排障时可以回答：

- 谁修改了 Deployment？
- 谁删除了 Secret？
- 哪个 ServiceAccount 创建了对象？
- 请求是否被拒绝？

## §4 认证 Authentication

### 4.1 普通 User

Kubernetes 本身通常不维护一个“普通用户对象”。用户身份由认证方式提供，例如：

- X.509 客户端证书
- OIDC
- Webhook Token
- 云厂商身份集成
- 其他认证插件

### 4.2 ServiceAccount

ServiceAccount 是 Kubernetes API 管理的对象，属于 Namespace，通常被 Pod 使用。

```bash
kubectl get sa
kubectl get sa default -o yaml
```

### 4.3 匿名请求

如果集群允许匿名访问，未认证请求可能被识别为匿名用户。生产集群应明确关闭不必要的匿名访问，并通过 RBAC 控制权限。

## §5 kubeconfig 与 X.509 用户

### 5.1 生成客户端密钥和 CSR

在客户端：

```bash
openssl genrsa -out laoma.key 2048
openssl req -new \
  -key laoma.key \
  -out laoma.csr \
  -subj '/CN=laoma/O=devops'
```

- `CN` 通常作为用户名
- `O` 可以作为用户所属组
- 私钥不能发送给管理员或提交仓库

### 5.2 管理员签发证书

管理员使用集群 CA 签名 CSR。实际命令依集群证书路径和流程为准：

```bash
openssl x509 -req \
  -in laoma.csr \
  -CA /etc/kubernetes/pki/ca.crt \
  -CAkey /etc/kubernetes/pki/ca.key \
  -CAcreateserial \
  -out laoma.crt \
  -days 365
```

CA 私钥属于最高敏感凭据，不能分发。

### 5.3 创建 kubeconfig

```bash
kubectl config set-cluster lab \
  --server=https://<api-server>:6443 \
  --certificate-authority=ca.crt \
  --embed-certs=true \
  --kubeconfig=laoma.config

kubectl config set-credentials laoma \
  --client-key=laoma.key \
  --client-certificate=laoma.crt \
  --embed-certs=true \
  --kubeconfig=laoma.config

kubectl config set-context laoma@lab \
  --cluster=lab \
  --user=laoma \
  --namespace=dev \
  --kubeconfig=laoma.config

kubectl config use-context laoma@lab --kubeconfig=laoma.config
```

### 5.4 认证与授权的边界

删除 Kubernetes 中的 CSR 对象不一定等于立刻撤销已签发的 X.509 证书。证书的有效期和 CA 信任链仍然重要。撤销策略必须由证书管理系统设计，不能只依赖删除 CSR。

## §6 授权 Authorization

Kubernetes 常见授权模式包括：

- `Node`
- `RBAC`
- `Webhook`
- `ABAC`（旧模式，通常不作为新集群首选）
- `AlwaysAllow` / `AlwaysDeny`（实验或特殊场景）

实际生产通常以 RBAC 为主，并使用最小权限。

授权判断维度：

```text
主体（User / Group / ServiceAccount）
+ API Group
+ Resource
+ Namespace
+ Verb
+ Subresource
```

常见 Verb：

```text
get list watch create update patch delete deletecollection
```

判断权限：

```bash
kubectl auth can-i get pods
kubectl auth can-i delete pods -n dev
kubectl auth can-i get secrets --as=laoma -n dev
kubectl auth can-i list pods \
  --as=system:serviceaccount:dev:app-sa \
  -n dev
```

## §7 Role、ClusterRole 与 Binding

### 7.1 Role

Role 只在某个 Namespace 内生效：

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: pod-reader
  namespace: dev
rules:
  - apiGroups: [""]
    resources: ["pods"]
    verbs: ["get", "list", "watch"]
```

### 7.2 RoleBinding

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: laoma-pod-reader
  namespace: dev
subjects:
  - kind: User
    name: laoma
    apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
```

RoleBinding 可以引用 ClusterRole，但授权仍然只作用于当前 Namespace。

### 7.3 ClusterRole

ClusterRole 可描述：

- 集群级资源权限
- 跨 Namespace 的权限
- 可被多个 Namespace 的 RoleBinding 引用

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: node-reader
rules:
  - apiGroups: [""]
    resources: ["nodes"]
    verbs: ["get", "list", "watch"]
```

### 7.4 ClusterRoleBinding

ClusterRoleBinding 把权限授予整个集群范围，风险较高：

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: ops-admin
subjects:
  - kind: Group
    name: ops
    apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: ClusterRole
  name: view
  apiGroup: rbac.authorization.k8s.io
```

`roleRef` 创建后不能随意修改；需要更换引用时通常删除并重建 Binding。

## §8 ServiceAccount

### 8.1 创建和绑定

```bash
kubectl create sa app-sa -n dev
kubectl get sa app-sa -n dev -o yaml
```

Pod 使用：

```yaml
spec:
  serviceAccountName: app-sa
  automountServiceAccountToken: false
```

默认不需要访问 API 的应用，建议关闭自动挂载：

```yaml
automountServiceAccountToken: false
```

### 8.2 ServiceAccount 与普通用户

| 维度 | 普通 User | ServiceAccount |
|---|---|---|
| 典型主体 | 人或外部客户端 | Pod 内程序 |
| 是否是 API 对象 | 通常不是 | 是 |
| 所属 Namespace | 不属于 | 属于 |
| 凭据 | 证书、OIDC 等 | Token 或短期 Token 投影 |
| 典型授权 | RoleBinding / ClusterRoleBinding | RoleBinding / ClusterRoleBinding |

### 8.3 Token

新版本更推荐短期、投影的 ServiceAccount Token，而不是长期 Secret Token。课堂中的手动 Token 实验适合理解机制，但生产环境应关注：

- Token 生命周期
- 是否自动挂载
- RBAC 权限
- 是否泄露到日志或镜像

## §9 SecurityContext 与宿主机安全

```yaml
spec:
  securityContext:
    runAsNonRoot: true
    seccompProfile:
      type: RuntimeDefault
  containers:
    - name: app
      image: app:1.0
      securityContext:
        allowPrivilegeEscalation: false
        readOnlyRootFilesystem: true
        capabilities:
          drop: ["ALL"]
```

常见安全控制：

- 不以 root 运行
- 禁止特权容器
- 删除不需要的 Linux Capability
- 只读根文件系统
- 使用临时目录承载可写数据
- 限制 HostNetwork、HostPID、HostPath
- 配置 Seccomp
- 配置 AppArmor 或 SELinux

### SELinux 联系

容器进程访问宿主机目录时，除了 Linux DAC 权限，还可能受到 SELinux MAC 策略影响。需要结合：

```bash
id
ls -Zd /path
ausearch -m avc -ts recent
restorecon -Rv /path
```

详见 [[LinuxSELinux]]。

## §10 Dashboard 与 Kuboard

Dashboard 和 Kuboard 可以作为学习和集群观察工具，但本质上仍然通过 Kubernetes API 工作：

```text
Web UI
  ↓
ServiceAccount / kubeconfig / Token
  ↓
API Server
  ↓
RBAC
```

部署时必须审查：

- 使用的镜像版本
- ServiceAccount 权限
- ClusterRoleBinding 范围
- 是否暴露到公网
- Token 生成和过期策略
- TLS 和访问入口

不要因为 UI 方便就给 Dashboard 绑定 `cluster-admin`。课堂中为了实验方便的高权限绑定，不能直接当成生产标准。

访问验证可以使用：

```bash
kubectl get deploy,svc,sa,role,rolebinding -n <dashboard-ns>
kubectl describe sa <name> -n <dashboard-ns>
kubectl auth can-i --list \
  --as=system:serviceaccount:<ns>:<sa>
```

## §11 安全排查

### `Unauthorized`

```bash
kubectl config current-context
kubectl config view --minify
kubectl get --raw='/version'
```

检查：

- kubeconfig 是否正确
- 证书是否过期
- CA 是否可信
- API Server 地址是否正确

### `Forbidden`

```bash
kubectl auth can-i <verb> <resource> -n <ns>
kubectl auth can-i --list
kubectl get role,rolebinding -n <ns>
kubectl get clusterrole,clusterrolebinding
```

检查：

- 当前身份
- Role 的资源和 verbs
- Binding 的 subject
- Binding 的 namespace
- 是否操作了子资源，如 `pods/log`

### Secret 泄露

处理步骤：

1. 立即停止继续传播
2. 轮换凭据
3. 检查 RBAC 读取范围
4. 检查日志、镜像和 Git 历史
5. 检查审计记录
6. 增加 Secret 管理和扫描

## §12 易错点

1. Secret 的 Base64 不是加密。
2. ConfigMap 不适合存密码。
3. Role 只在 Namespace 内生效。
4. ClusterRole 可以被 RoleBinding 引用，但作用范围仍由 Binding 决定。
5. `roleRef` 不是随意可修改字段。
6. ServiceAccount 不是普通人类用户。
7. 删除 CSR 不等于撤销已签发证书。
8. Dashboard 方便不等于安全。
9. `cluster-admin` 不应该作为默认应用权限。
10. 不需要访问 API 的 Pod 应考虑关闭 Token 自动挂载。
11. Namespace 不是单独的多租户安全方案。
12. RBAC 只管 API 权限，不直接管 Pod 网络流量。

## §13 面试追问

### Q1：API 请求的认证、授权和准入有什么区别？

认证识别请求者是谁；授权判断该主体是否有执行动作的权限；准入控制在授权之后对请求进行进一步修改或拒绝。

### Q2：Role 和 ClusterRole 的区别？

Role 是 Namespace 作用域的权限定义；ClusterRole 可以定义集群级资源或跨 Namespace 权限。最终范围还要看 RoleBinding 或 ClusterRoleBinding。

### Q3：Secret 安全吗？

Secret 只是 Kubernetes 对敏感配置的抽象，默认 `data` 只是 Base64。真正安全需要 RBAC、etcd 加密、传输保护、凭据轮换和外部 Secret 管理。

### Q4：ServiceAccount Token 为什么危险？

Pod 如果自动挂载 Token，应用一旦被入侵，攻击者可能使用该身份访问 API。因此必须使用最小权限，并关闭不需要的自动挂载。
